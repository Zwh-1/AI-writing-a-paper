# 0.3.3 DeepSeek 资料整理修复

## 实际问题

用户配置真实 key 后，接口已成功响应，但页面把排队状态显示为“正在整理 · 0%”，且单个后台进程需要依次完成每份资料的分段调用。模型默认的长推理增加了等待时间和输出截断风险。每次未知费用预留 2 个项目预算单位，10 次调用就占满项目的 20；这不是已实际扣费 20。

## 修复内容

- 排队与执行分开显示；排队显示前方任务数，执行显示当前分段、原文页范围和百分比。
- 资料页增加批量进度，分别显示完成、排队、执行、预算待核对和失败。资料列表显示每份总结状态，可直接打开已完成结果。
- DeepSeek 总结默认发送 `thinking: {type: "disabled"}`。保留用户选中的模型 ID，并在高级设置提供推理开关、输出上限及每次预算预留。
- 核对服务商 `/v1/usage` 的账单汇总。仅在专用密钥范围、模型、请求数、项目、币种及 Token 数能够匹配时，用服务商返回费用字段的较大值替代这些请求的预算预留。
- 汇总账单独立存储，不伪造每个请求的精确费用；原始用量、预留和响应保持可追溯。无法匹配、正在执行、远端状态未知或涉及多个项目时保留预留。
- 对旧记录核对 DPAPI 密钥保存时间；新请求记录不可逆的凭据指纹，避免换 key 后错误归属账单。旧账单快照不能覆盖已核对的更多请求，也不能降低人工确认的费用。
- 预算不足时显示“预算待核对”，可点击“核对账单并继续”。预算耗尽前，后台也会尝试严格核对账单，而不是提高项目预算或删除未知费用记录。
- 输出截断时保留响应正文和实际用量，标记为已返回但无效，避免把已消耗 Token 的请求当作执行前拒绝。未知远端结果不会被批量操作自动重发。
- 支持下载带页码的 Markdown 总结。检索召回评测和批量 OCR 移到资料列表之后，资料页优先展示总结和资料。

## 实际数据恢复

- 修复前保存了数据库快照：`data/backups/summary-before-v0.3.3.sqlite3`。
- 初次核对 11 次已发生的请求（含一次已明确截断的响应），服务商汇总费用字段的较大值为 0.28685 USD。本地预算占用由预留 20 恢复为对应账单金额；未提高项目的 20 预算上限。
- 续跑 22 份被本地预算拦住的任务，并为一份已明确截断的资料复用成功片段继续处理。未重发远端结果未知的请求。
- 最终 25/25 份资料全部完成，覆盖 655/655 个有文字的页面，未留下排队、执行、预算阻塞或失败任务。49 次真实请求的账单范围核对通过，汇总核算保守值为 0.670913 USD；这不是对实际优惠扣费金额的推断。详见 `material-summary-live-results.json`。

## 使用

重新打开本机启动器即可进入更新后的工作台。资料中心可直接查看批量完成情况，点击文件名或“概括与分点”阅读总结。若未来服务商账单不能与本机记录严格匹配，页面会保留预留，并提供核对原因。
