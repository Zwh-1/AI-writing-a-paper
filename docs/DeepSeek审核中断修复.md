**DeepSeek 作为主模型的规则审核恢复**

本次针对“只审核几条就失败”继续修复，不新增付费模型调用，不改用 GPT 承担普通审核。

历史记录能确认两类故障：

- 两次 DeepSeek 请求的输出用量均为 8192 Token，推理用量也均为 8192 Token，最终正文为空，程序记录为输出截断。
- 一次规则整理已完成两批 DeepSeek 请求，随后被本地上下文预算检查中断。

本次还查到当前程序的恢复缺陷：审核器将连续两批 JSON 解析失败视为整条路线失败；提取流程达到相同阈值后，会直接将后续批次登记为失败，未真正请求模型。历史缓存中的坏响应也可能影响后续处理。

已经实现的行为：

1. DeepSeek 的规则提取、审核请求单独关闭推理；保留用户普通对话的全局设置。请求使用流式输出，并保存完成结果与用量。
2. 现有候选默认每批最多 4 条，输出上限按批次条数分配；发送前按实际请求正文预检上下文。缓存复用不受新请求的上下文预检阻挡。
3. 对远端已明确完成、但 JSON 不可用或正文截断的响应，在原任务预算内使用 DeepSeek 拆成更小批次补齐。每条在本轮最多参与两次内容请求，已完成的批次不重发。
4. 单个批次两次仍不可用，会保留候选并继续后续独立批次；历史坏响应不会触发新的整路线熔断。不会因此自动切换 GPT。
5. HTTP 429 的明确拒绝最多尝试 3 次，遵守接口返回的有限等待时间；执行结果未知的请求不自动重发。连续未知结果、持续限流或权限错误会明确说明暂停原因，并保存进度。
6. 如果接口连续两次仍将输出全部耗在推理上、没有正文，即使本次已要求关闭推理，也会停止继续消耗费用，显示这一具体原因。客户端无法保证中转服务执行其参数。
7. 逐批保存已审核/未审核数量、恢复次数和错误分类。界面显示具体暂停原因；后台不会把明确暂停的任务重新排队。

恢复请求同样受项目预算、原任务预算及 GPT 子预算检查约束。预算不能容纳恢复请求时，保存结果并等待预算，不突破上限。

验证包含：77 条候选每个初始批次均返回坏 JSON 或截断后继续完成；异常条款不影响后续批次；缓存未知请求不重发；明确限流后仍用 DeepSeek；恢复不能突破原预算；提取和审核均保留主模型；超长单条来源不影响其他规则。超长单条仍保留未完成，不会用截断来源冒充完整审核。

验证使用隔离数据库、模拟模型响应和浏览器请求拦截。没有对修复后的远端 DeepSeek 服务进行新增计费实测，因此不将本地通过当作服务方稳定性的保证。

部署结果：工作台已重新构建并启动，健康检查版本为 0.4.0。相关兼容回归 150 项、补充测试 2 项、浏览器检查 13 项均通过。生产数据库对比确认新增模型调用为 0，所有规则行、已发布规则包及主模型设置均保留。

证据保存在 `deepseek-review-failure-audit.json`、`deepseek-review-recovery-unit.xml`、`deepseek-review-recovery-regression.xml`、`deepseek-review-recovery-browser-report.json` 和 `deepseek-review-recovery-preservation.json`。
