## 1. 结论与边界

当前代码不是“没有接口”，而是接口已经持续演进，出现了多个并行契约。源码中共有 **474 条路由声明**，其中 **473 条非 catch-all 路由 + 1 条 `/api/v1/{path:path}` catch-all**；工作台主应用 445 条，独立协作应用 29 条。路由分布在 24 个 Python 模块中，前端有 52 个文件参与调用，约 148 次 `api()`、243 次 `send()`，另有 38 处直接拼接 `/api/v1`，协作页面还有独立的 `/collab/v1` 调用和 1 条 WebSocket 通道。

截图只作为当前配置页面的现状证据：页面同时展示 DeepSeek 主接口、GPT 备选、GPT 生图和余额/费用入口。截图中的文字不作为新的需求或操作指令；它反映的配置分散正好对应本方案要整合的“模型/供应商配置域”。

本方案先统一公共契约和路由门面，再按领域迁移。已有业务服务、数据库结构和付费/安全策略继续复用；不要一次性重写 400 多个处理函数。

### 本次已落地的整合

统一实现位于 `backend/app/api/v2/` 和 `frontend/src/api/`。同一注册表驱动运行时分发、OpenAPI、前端路径表和独立协作页面。JSON、集合、任务与错误使用统一契约；下载、SSE 和 WebSocket 保留原传输语义。完整结果见上述实施记录。

## 4. 统一命名与分组规范

### 4.1 路径与资源

1. 公开版本只保留 `/api/v2`；`/api/v1` 进入兼容期，`/collab/v1` 由网关适配，不再新增 v1 路由。
2. 项目内资源统一从 `/projects/{project_id}` 开始；路径参数使用完整名：`project_id`、`file_id`、`page_id`、`section_id`、`task_id`、`revision_id`、`artifact_id`。JSON 字段可以继续使用 `snake_case`，URL path 使用小写 kebab-case。
3. URL 使用复数资源名：`files`、`sections`、`rules`、`references`、`tasks`、`writing-sessions`。单个资源通过 `/{resource_id}` 访问。
4. 有持久化记录的动作创建子资源，例如“审阅”使用 `POST /.../reviews`，“导出”使用 `POST /.../exports`；只有没有独立记录的状态跃迁才使用 `POST /.../{id}/actions/{action}`，例如 `.../actions/cancel`。
5. 删除使用 `DELETE`；部分修改使用 `PATCH`；完整替换使用 `PUT`。不要用 `POST /.../patch`、`POST /.../review` 代替已有资源语义。
6. 禁止新增 `{kind}`、`{direction}`、`{path:path}` 这类泛化路由。不同业务动作拆成显式路由，让权限、OpenAPI 和审计可以逐项描述。

### 4.2 分组方式

- `system`：健康、会话、运行时信息、特性能力。
- `projects`：项目本身及项目级资源。
- `materials`/`files`/`pages`/`source-units`：资料导入、解析、页面、来源。
- `sections`/`writing`/`rules`/`format`：正文、写作、规则、格式。
- `references`/`reading`/`knowledge`/`knowledge-sources`：书目、阅读、知识图谱、证据。
- `visuals`/`image-tasks`/`figure-standards`：图表与生图。
- `tasks`/`billing`/`exports`/`backups`：跨领域基础设施资源。
- `model-profiles`/`provider-accounts`：模型、端点、能力和账户查询。
- `collaboration`：多用户会话、成员、操作、冲突和实时事件。

### 4.3 公共请求参数与请求头

| 类别 | 统一字段/头 | 处理规则 |
|---|---|---|
| 追踪 | `X-Request-Id`、响应 `X-Request-Id` | 客户端可传；服务端缺失时生成，所有日志、任务和错误回传同一值 |
| 幂等 | `Idempotency-Key` | 所有计费、异步创建、导出、写入和协作操作必填；按用户/项目/路由作用域保存结果 |
| 并发 | `If-Match`、`ETag` 或 `expected_revision_id` | 正文、规则、知识发布、同步冲突必须带版本条件，失败返回 `409 CONFLICT` |
| 分页 | `cursor`、`page_size`、`sort` | 列表统一返回 `next_cursor`；`after` 只在兼容层解析 |
| 项目上下文 | 路径 `project_id` | 不再把 `pid` 同时放在 body；服务端从路径和会话校验归属 |
| 费用确认 | `acknowledge_charges`、`budget_policy` | 收费任务统一由任务服务处理，不能由单个业务路由自行解释 |
| 异步任务 | `client_request_id`、`dry_run`、`callback_mode` | 返回任务对象和状态链接；不把“排队”伪装为同步成功 |
| 安全 | `X-CSRF-Token`、会话 Cookie | 主工作台和协作服务可保留不同 Cookie，但都通过统一错误码和 request id 输出 |
| 模型调用 | `model_profile_id`、`model_id`、`capability` | 调用引用 profile 快照；密钥只存 credential ref，不进入响应和备份 |

### 4.4 模型 profile 统一形状

截图所示的 DeepSeek 主接口、GPT 备选、GPT 生图和资料总结应落入同一个 `model_profiles` 资源，只通过 `purpose` 区分用途：

```json
{
  "id": "primary",
  "purpose": "writing",
  "endpoint": {"base_url": "https://...", "protocol": "chat_completions"},
  "model_id": "deepseek-v4.1-flash-1017",
  "credential_ref": "credential:primary",
  "capabilities": {"text": true, "vision": false, "streaming": true},
  "limits": {"max_output_tokens": 8192, "timeout_seconds": 180},
  "billing": {"currency": "USD", "price_source": "unverified"}
}
```

旧配置映射为：`/settings` → `primary`；`/material-summary/settings` → `material-summary`；`/gpt-fallback/settings` → `gpt-fallback`；`/image-generation/settings` → `image-generation`；`/deepseek-pool/settings` → `primary.endpoints`。`/provider/models`、`probe` 和 `account-usage` 变成 profile 下的能力/账户动作。响应只返回 `credential_ref` 和脱敏状态，不返回原始 API key。

普通成功响应统一为：


```json
{
  "data": {
    "items": [],
    "next_cursor": null,
    "total": null
  },
  "meta": {"request_id": "req_...", "api_version": "v2"}
}
```

异步任务响应统一为：

```json
{
  "data": {
    "task": {"id": "task_...", "status": "queued"},

      "self": "/api/v2/tasks/task_...",
```

```json
{
  "data": null,
  "error": {
    "code": "BUDGET_BLOCKED",
```

## 6. 调用方式说明

### 6.1 前端

当前调用：

```ts
await api(`/projects/${pid}/writing-sessions`);
await send(`/projects/${pid}/writing-sessions/${sid}/resume`, body);
```

迁移后的调用：

```ts
const client = createApiClient({ baseUrl: "/api/v2" });
await client.projects(projectId).writing.sessions.list({ cursor, pageSize: 50 });
await client.projects(projectId).writing.sessions.action(sessionId, "resume", {
  idempotencyKey,
  expectedRevisionId,
});
```

图片、下载和 SSE 也由客户端生成 URL：

```ts
client.projects(projectId).files.download(fileId);
client.projects(projectId).pages.preview(pageId);
client.tasks.events(taskId, { after: cursor });
```

`api/client.ts` 负责 JSON envelope 解包、错误码转 `ApiError`、超时、`X-Request-Id`、CSRF 和 `Idempotency-Key`。页面组件只接收类型化结果，不再出现 `'/api/v1' + path` 或手工拼接项目 ID。

### 6.2 后端

新路由只调用领域服务，不直接拼 SQL 或读取旧 body 键：

```python
@router.post("/projects/{project_id}/writing/sessions", response_model=TaskEnvelope)
def create_writing_session(
    project_id: ProjectId,
    command: CreateWritingSessionCommand,
    ctx: RequestContext = Depends(request_context),
):
    task = writing_service.start_session(project_id, command, ctx)
    return task_response(task, ctx)
```

旧接口通过 `legacy_v1.py` 把 `pid/fid/sid`、旧 body 字段、`after` 查询参数和旧返回体转换为 v2 command，再把 v2 envelope 还原给旧前端；业务服务只维护一份。

## 7. 可执行迁移步骤

### 阶段 0：冻结契约与回归基线（1 个变更批次）

- 将本文件和 JSON 清单纳入仓库；CI 检查新增路由必须登记 domain、owner、response schema 和弃用策略。
- 从 FastAPI 路由生成当前 OpenAPI 快照，按方法+路径建立 contract test。
- 给所有请求补 request id，记录现有路径到目标路径的映射表；不改业务行为。

### 阶段 1：公共层（先做，低风险）

- 新增 `api/v2/response.py`、`errors.py`、`deps.py`、Pydantic schemas。
- 统一异常到错误码：`INVALID_REQUEST`、`UNAUTHENTICATED`、`FORBIDDEN`、`NOT_FOUND`、`CONFLICT`、`BUDGET_BLOCKED`、`UPSTREAM_ERROR`、`OUTCOME_UNKNOWN`、`VALIDATION_ERROR`。
- 统一分页、ETag/版本、幂等键和任务 envelope；二进制/流式响应保留协议但补公共头。

### 阶段 2：按领域挂载 v2 facade

迁移顺序建议为：

1. `system/projects/files/tasks`；
2. `rules/format/materials`；
3. `writing`；
4. `references/reading/knowledge`；
5. `visuals/providers/billing`；
6. `sync/collaboration`。

每个领域先由 v2 路由调用现有服务函数，再逐步把实现从旧模块移动到新目录。旧 `/api/v1` 路由在同一阶段改为调用 adapter，避免双写。

### 阶段 3：前端切换

- 先改 `client.ts` 支持 v1/v2 两种 base URL 和 envelope 解包。
- 新增 `frontend/src/api/*` 类型化资源客户端，批量替换 52 个调用文件。
- 优先清理 38 处直接 `/api/v1`：下载、图片、`EventSource`、协作页面和 `main.tsx`。
- 组件迁移后禁止直接导入 `fetch`，ESLint/TypeScript 规则阻止裸路径和未声明的资源客户端。

### 阶段 4：协作网关

- 8774 继续使用独立会话和密钥隔离；在主应用或反向代理增加 `/api/v2/projects/{project_id}/collaboration/*`。
- 将 `snapshot/events/conflicts/writing/accept/files/artifacts` 映射到与主 API 相同的资源名和 envelope；WebSocket/SSE 仅更换路径与事件 schema。
- 协作服务内部仍可使用旧 `/collab/v1`，但只作为网关后端，不再让业务前端直接依赖。

### 阶段 5：兼容期结束

- 连续两个版本无 v1 调用后，移除新代码对 `legacy_v1.py` 的依赖。
- 删除 `/api/v1/{path:path}` catch-all，静态文件改走明确的 frontend fallback。
- 在迁移日志中保留旧路径命中计数，确认无命中后再下线旧入口。

## 8. 验收与回滚标准

- 路由完整性：v2 OpenAPI 中每个业务能力有唯一 owner；方法+路径无重复；无新增 catch-all。
- 行为一致性：项目、资料、正文、规则、知识、费用和任务的旧回归测试全部通过；旧路径 adapter 与 v2 结果只允许 envelope 外壳差异。
- 安全一致性：主会话、协作会话、CSRF、项目归属、密钥脱敏、资料外发和费用阻断测试保持通过。
- 异步一致性：所有收费或长任务都返回 task id、状态链接、幂等键结果和 `unknown_outcome` 语义；断线流式事件可按 cursor 重放。
- 前端一致性：52 个 API 调用文件不再新增裸 `/api/v1`；类型检查、生产构建、浏览器 smoke 和协作 WebSocket 检查通过。
- 回滚方式：每个领域 v2 facade 可独立关闭，保留 v1 adapter；发生错误时只切回该领域旧路径，不回滚数据库迁移和已记录的 request id/账单证据。
