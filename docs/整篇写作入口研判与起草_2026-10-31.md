# 整篇写作入口的研判、起草与预估（2026-10-31）

整篇写作原来的入口只有一段空白的要求输入框、一个可用预算和一行“9 个章节 / 15,150 字”。用户要自己决定写什么、分几章、够不够写、要花多少钱，程序只回答“能不能开始”。这一轮把这个入口改成先读项目、再给建议，用户仍然可以全部覆盖。

## 打开对话框先读一遍项目

新增只读接口 `GET /projects/{pid}/paper-writing/study`（`backend/app/paper_study.py`）。它只读本地记录，不发模型请求、不预留预算、不写任何表，因此反复打开不产生费用。

- 结构：章数、正文目标字数、已有正文的章数、篇幅最大的章及其占比。
- 章节画像：每章的类型、层级、目标字数、写作目标（来自章节任务，缺省回落到章节目标）、可加载依据条数（章节任务的 `evidence_ids`）、关联事实数、已有正文字数。
- 依据盘点：研究事实总数与实测条数、事实是否关联来源、参考文献总数与已核对条数、资料份数与规则资料份数、图表数、术语条数、当前代码快照的代码单元数。
- 风险清单：按“先处理 / 建议处理 / 提示”三级，每条给出针对该项目的具体处理建议。

风险规则不是通用提醒，而是按章节类型与记录状态判断。例如结果类章节存在但没有任何研究事实、事实存在但没有一条是实测、文献类章节存在但文献表为空、需求或设计或实现类章节没有绑定代码快照、单章占比超过全篇 45%、各章字数合计与项目目标字数相差超过 15%、题目或研究问题仍是占位式表述。每条都写明是哪一章、差多少、先补什么。

## 整篇写作要求自动起草

`requirement_draft` 用本地记录拼出一段可直接使用的要求，分四段：全篇要回答的问题与不写什么、各章按标题与目标字数的分工、可用依据与缺口写法、术语与表达口径。

- 研究问题取项目简报的 `question`，为空时取写作核心的 `research_question`；两者都是“围绕‘我的毕业论文’组织……”这类占位表述时不再引用，改为“全文按提纲确定的问题和范围展开”，避免把占位句写进模型指令。
- 章节分工优先用章节任务里写的目标；仍是默认句时改用该章类型的角色说明，并且只取第一个分句，不会截断成半个词。
- 依据段写出实际条数与“【待补证据】”的写法；当结果章没有实测事实时追加一句“只写测试设计、验证方式与现状说明，不给出通过率或性能结论”。
- 前端在首次打开时把它填进输入框，并标注“已按提纲、研究事实与资料范围起草，可直接修改”。用户改过之后不会被覆盖，需要时点“恢复研判草案”。

## 费用预估

`estimate` 按章给出输入与输出 token 与金额。价格沿用现有的计价链路（`paper_writing.config_for` → `expense_evidence.resolve_config` → `summary_billing.priced_config`），未登记单价时只给 token，不猜金额。输入 token 有两种口径：本项目此前有三次以上整篇请求时用实际用量的均值；否则按“每章约 8 千字上下文，加上此前各章的累计字数”推算。两种口径在界面上都写明来源，并注明实际按请求计费。

界面上显示为一行：“预计花费 USD 0.2800，共 9 次请求，输入约 11.7 万 token、输出约 4.1 万 token。”旁边的“按预计填入预算”按预估值的 1.25 倍填，并且不超过项目可用预算。

## 运行与审阅阶段的可见性

- 每写完一章，`run()` 记录该章的字数、目标字数、引用数、图表数、待补标记数与缺失材料条数（`output.section_checks`）。界面在进度条下方列出，字数不足目标 60% 的章标红并写“明显不足，建议修订”。
- 审阅接口新增 `advice`，把本地检查结论转写成一段修订要求，按问题严重程度最多点名五章，写明结构问题、待补标记与字数差，并交代“其余章节保持不变，结论与摘要按修改后的正文联动更新”。界面提供“按审阅结果起草要求”，填入后仍可修改。

## 边界

研判不替代预检：预算、规则包、依赖环这些阻塞项仍由 `preflight` 判断，研判只解释“为什么值得先补”，不会自动修改提纲、事实或术语。它也不判断内容真实性，只回答“按现有记录能写出什么、缺什么”。占位题目与研究问题的识别是模式匹配，改写后会在下一次打开时立即消失。

## 验证

- 新增 `tests/test_paper_study.py` 五项：结果章无事实时的风险、研判不产生任务与费用与版本记录、预估与章节一一对应、占位研究问题不被引用进草案、审阅建议的措辞与空报告返回空串。全部通过。
- `tests/test_paper_writing.py` 十六项通过。其中一次运行末尾出现 `PytestUnhandledThreadExceptionWarning`（残留线程在临时库关闭后仍尝试写入，报 readonly database），该用例单独复跑通过，第二次整文件复跑十六项全过，与本轮改动无关，属测试进程线程清理的既有偶发。
- 整篇写作浏览器流程 `tests/paper-writing-browser.cjs` 六项检查全部通过：入口与三档宽度、一次生成完整候选、关闭重开保留候选、按审阅问题修订、整体写入、预算中断后继续；页面脚本无报错，接口无 4xx/5xx。
- `npm run build`（含 `tsc --noEmit`）通过。
- 真实项目数据（9 章、15,150 字、31 篇文献、33 份资料、79,507 个代码单元）在数据库一致副本上只读复算：3 项先处理、1 项建议处理、3 项提示；预估 USD 0.2801，9 次请求，输入 11.7 万 token、输出 4.1 万 token。截图见 `.runtime/study-check/shots/`。
- 全量回归共 1449 项，本次未跑完（单文件耗时多在数十秒）；已完成的段落中出现的两处失败位于账户用量与接口迁移两个未改动模块，单独复跑均通过。

## 生效方式

后端新增了接口，前端已重新构建。需要从启动器重新打开工作台（或重启 8765 端口的服务与 worker）才会加载新接口；只刷新页面时研判卡片不出现，其余入口与原来一致。
