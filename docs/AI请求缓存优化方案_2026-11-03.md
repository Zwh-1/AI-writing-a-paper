## 2. 缓存层和已经存在的机制

1. **服务商前缀缓存**：截图统计的是已经发送出去的输入 token，其中一部分复用服务端计算。应用里的 Redis、LRU、结果缓存不能直接代替它。
2. **本地完整响应缓存**：命中后整次 HTTP 不再发生，也不应计为“又命中一次服务商输入缓存”。写作恢复与知识编译已有此机制。
3. **本地计算缓存**：向量、重排、解析与权限校验范围内的缓存减少 CPU/IO；不应把其命中率作为 API token 节省率。

已有实现：

- `backend/app/retrieval.py:55`：查询向量 LRU 128 项，模型指纹参与键；锁分片及二次检查避免同查询重复计算。
- `backend/app/retrieval.py:114`：重排 LRU 2,048 项；`:138` 数值矩阵最多 8 项、96 MiB。
- `backend/app/knowledge_units.py:14`：ContextVar 输入/读取缓存，仅在单次操作范围内有效，避免权限撤销或原件变化被长期缓存遮蔽。
- `backend/app/knowledge_model_bridge.py:8`：已有跨进程 FileLock；SQLite 完成响应复用；命中前校验来源；未知请求不自动重发。
- `backend/app/writing_flow.py:232`：按任务、阶段、序号和输入版本复用完成响应，保留恢复及防重复扣费保护。
- `backend/app/writing_request.py:50`：已对逐字相同的来源、阅读回执与单元文本做去重。

未发现这些关键缓存采用了一个可以解释截图的“过短 TTL”。延长 TTL 或先引入 Redis，不能解决动态字段先打断公共前缀的问题。

## 3. 有代码和历史记录支持的根因

### A. 动态任务信息排在大段共享材料之前，优先级最高

- `backend/app/writing_flow.py:482–492`：当前源码把单元序号、总数、字数写进 system，修复时继续追加尝试次数和错误；system 在 user 中的全部材料之前发送。
- `backend/app/writing_flow.py:613–624`：核验请求先放 `expected_claim_ids`、章节、claims，之后才放 `actual_sources`；换批次先改变前面的字段。
- `backend/app/tasks.py:661,752`：普通写作按 project、section、operation、instruction、rules、facts、sources 等构造和发送上下文；章节 ID、revision、用户指令变化早于长段规则与原文。
- `backend/app/tasks.py:701,844`：不同操作目标及格式修复信息也进入 system。

历史旁证：窗口内 4 次单元修复保存了 4 份不同 system，其共同前缀仅 2,951 个字符，每次完整请求平均约 426,705 个字符。字符数不是 token 数，但能确认大量后续文本位于 system 首个差异之后。语义核验的25条记录（24条有用量）所保存的 system 完全相同，说明其低命中应重点检查 user 前部的批次/主张变化。

这些证据能解释前缀被打断的机制，但不能将全部 79.02% 未命中精确归因给某一字段；第一次冷请求、不同来源组合、上游清理也会产生正常 miss。

### B. 线上序列化缺少统一的确定性约定

- `backend/app/db.py:10` 的 `dumps()` 不排序键；`backend/app/writing_agent/common.py:5` 的 digest 却按键排序。因此“本地内容哈希一致”不代表“线上文本字节相同”。
- `backend/app/document_preparation.py:113–122` 从 `file_ids` 集合直接迭代构造来源，不同进程间顺序可能变化。
- `backend/app/tasks.py:567,638` 的部分 facts、bibliography、terms 查询缺少 `ORDER BY`。
- facts 整行进入模型视图，包含非正文的 created_at/updated_at；这些字段应保留在本地版本清单，而不是无差别发送。

不能盲目排序所有列表：章节、段落、对话、工具调用、引用顺序以及检索优先级可能具有语义。

### C. 同一写作任务反复发送大上下文，放大了 miss 成本

- `backend/app/paper_writing.py:300–314`：后续章节携带此前候选全文。
- `backend/app/writing_continuity.py:20–48`：默认提供全部已有章节。
- `backend/app/writing_flow.py:402–416`：单元继承完整 context，再加入章节背景及之前单元正文。
- `backend/app/writing_flow.py:619–624`：每个核验批次仍携带 candidate_paragraphs、related_sections、paper_draft_sections。

当前源码的 `writing_request.compact_model_context()` / `expand_model_context()` 已有可逆的精确重复块引用，`writing_flow._cached_call()` 和 `tasks._writing()` 已接入该视图。实施时先使用已有 `component_bytes/canonical_component_bytes` 度量其覆盖范围，再修正前缀布局；不能把已有去重当成尚未实现，也不能再叠加不兼容的第二套引用协议。进一步缩小范围必须走现有明确的 `argument_scoped` 和覆盖声明，不能用截断原文或删除强制规则来制造“省 token”。

### D. 用量与费用的观测存在明确缺口，但它不制造上游 miss

- `backend/app/adapter.py:308` 只统一输入/输出总数，未统一命中/未命中字段。
- 普通、pool、stream、agent 分别处理 usage；Responses 流式及 agent 有的直接保存原始 usage，现有只读取 `usage.raw` 的统计会漏掉它。
- 离线已复现：仅有 `prompt_tokens_details.cached_tokens=80` 时，当前 normalize_usage 会错误推断总输入为 80；布尔值也被当作整数接收。
- `backend/app/provider.py` 的 `usage_cost()` 统一按输入单价计全部输入，没有明确的缓存分价证据。这可能高估本地估算，不能据此改写服务商账单。
- `backend/app/tasks.py` 的 `_metered_model_call()` 未统一持久化实际成功路由的 `provider_snapshot`；某些 pool 历史记录只有接口名称。诊断时不能用切换前的 provider 冒充实际目标。下文涉及已变动调用链以函数名为定位锚，较早审计行号只作参考。

### E. 并发和索引可改善，但不是这张图已证实的主要原因

- 写作 `_cached_call` 未发现覆盖“查缓存—预留—发送—保存”的阶段单飞锁；知识模型请求已有 FileLock。
- 在真实库只读执行 `EXPLAIN QUERY PLAN`：写作缓存查找出现 `SCAN generation_runs` 和 `USE TEMP B-TREE FOR ORDER BY`。目前仅有主键及费用用途索引，没有任务/时间缓存查找索引。
- 这会增加恢复和并发开销，但截图不能证明发生了并发击穿。

尚未证实的因素：服务端实际 TTL、清理、路由到不同上游、当时轮询策略、缓存窗口或分片限制。需要供应商能力说明和分组指标，不能从聚合图推断。

## 4. 具体实施方案

### P0：先统一可观测性和基线

统一 usage 契约：

```json
{
  "input_tokens": 1000,
  "output_tokens": 100,
  "cache_hit_tokens": 800,
  "cache_miss_tokens": 200,
  "cache_reporting": "reported_or_validated_derived",
  "raw": {}
}
```

支持 DeepSeek 顶层 hit/miss、Chat 的 prompt_tokens_details.cached_tokens、Responses 的 input_tokens_details.cached_tokens；所有 transport 调用同一个归一化函数。严格排除 bool、负数、hit 大于总输入及互相冲突的字段。缺失或矛盾保持 null/unknown，不补零、不从单个缓存子计数猜总输入。仅对已确认的 OpenAI/Responses 计数语义，在总输入与命中都有效时推导 miss。保留 raw 和字段来源。

保存实际成功的 endpoint/model/protocol 快照、时间口径、prompt_layout_version、稳定块摘要、各块字符/字节数、本地响应是否复用及未命中原因。无须新增正文日志或记录密钥；历史账本不回填伪造的字段。

### P1：固定 system，把稳定材料放前、动态任务放后

新增 `backend/app/prompt_layout.py`，独立于全局 `db.dumps`。所有普通、pool、stream、agent 的模型视图使用共同的布局/构造入口；保持原有协议能力与工具消息顺序。

```text
system：固定的阶段指令、安全边界、输出协议说明（带模板版本）

user.data.stable：
  规则与范围 → 术语 → 稳定排序的已选来源和完整原文 → 静态参考材料

user.data.task：
  当前章节 → 用户指令 → 当前单元/目标字数 → 当前 claims
  → 已完成正文和依赖 → 修复次数、错误及待修复候选
```

实现为一个有固定顶层顺序的消息/JSON 数据视图；稳定块内部使用确定性的 JSON 序列化。资料仍位于 user 数据，不把原文提升为 system 指令。

具体规则：

- 把 `unit_system` 里的单元参数以及 repair error 移到任务尾部，固定各阶段 system。
- 核验的来源材料排在批次 claims 前；共享来源只保留一次，批次通过 ID 精确引用。
- file_ids 用明确稳定顺序；无语义顺序的 facts/terms/refs 以稳定 ID 或业务排序字段加 ID 排序；有语义顺序的列表原样保留。
- 不做全局去空格、小写、Unicode 兼容折叠或模糊相似合并，防止原文、公式、代码和引用被改变。
- 不把当前时间、任务 UUID、请求 UUID、费用估算等运行信息放在共享前缀中；审计与权限字段留在 manifest。
- 来源集合未变时保持同一阶段的材料顺序；新检索结果按有版本的选择快照处理，不能无校验地冻结过期材料。
- 新任务固定 `prompt_layout_version=cache_v2`；运行中的旧任务继续 legacy，不能在任务中途切换布局或缓存键。

实现顺序必须明确：先按业务语义构造稳定/动态块并对允许排序的集合排序，再运行现有精确引用压缩，最后序列化。不对已经生成带数组位置的引用视图再重排数组；必须断言 `expand_model_context(compact_model_context(context)) == context`。流式和非流式使用相同模型视图；agent 只处理新任务输入数据块，不重排现有对话、工具调用和 Responses items。

### P2：规范任务内缓存键，保留恢复安全边界

不要把服务商缓存键、本地完整响应键和运输请求 ID 混为一谈。

**稳定材料块键（L1，可复用组装结果）**：

```text
SHA256(canonical_json({
  schema: "prompt-block.v2",
  project_id, stage, layout_version, system_template_version, model_view_version,
  rule_package_hash, terminology_hash,
  sources: [{file_id, original_sha256, parse_head, range, text_hash, use_policy_revision}]
}))
```

数组仅在被声明为无序集合时规范排序。命中后仍验证当前权限与来源版本。可先采用进程内 LRU 128 项、总计 32 MiB 作为可调上限；按实际 UTF-8 字节计容量，单项超过总容量不入缓存，命中返回不可变视图或深拷贝，锁内更新 LRU，数值计算不持有全局缓存锁。容量是初始工程参数，不是实测最优值。TTL 仅用于内存回收，不作为权限有效性或远端是否执行的依据。

**任务内语义恢复键（L2，只复用本任务已完成的响应）**：

```text
SHA256(canonical_json({
  schema: "writing-recovery.v2", database_namespace, project_id, task_id,
  section_id, stage, logical_unit_index, layout_version, system_template_version,
  model_view_version, generation_intent_revision, complete_semantic_input_digest, image_digests,
  tools_and_output_schema_digest,
  rule_and_source_versions, use_policy_revision
}))
```

这个键包含 task_id，禁止跨写作任务查找或复用。已经完成的同任务阶段允许在恢复时更换端点，命中后不发送新请求；不因输运超时、重试次数、价格或端点变化而丢失可恢复结果。任务输入、规则、原文及当前权限仍必须匹配，语义变更不命中。显式改变随机种子、温度、推理要求或要求新候选属于生成意图变更，应更新 generation_intent_revision/逻辑操作标识，不能复用旧输出；纯故障恢复不自动更新该字段，也不能删除旧完成结果或未确认记录。

**实际发送键（wire fingerprint，区分真实请求，不直接作为恢复资格）**：

```text
SHA256(canonical_json({
  schema: "ai-wire.v2", database_namespace, project_id, task_id, stage, logical_unit_index,
  layout_version, endpoint_namespace, credential_fingerprint, model_and_revision, protocol,
  complete_payload_digest, image_digests, tools_and_output_schema_digest,
  generation_options: {max_output_tokens, temperature, top_p, seed, thinking, reasoning}
}))
```

endpoint_namespace 规范协议、主机、默认端口和尾部斜杠，保留 API path/tenant 区别；credential 使用单向摘要，不输出到公共日志。文本保持精确，不做语义近似缓存。先查合法的任务内完成响应；只有 miss 后，才根据有效路线和实际配置生成 wire fingerprint。保留现有 `writing_flow_content_hash`、`writing_flow_request_hash`、`_legacy_cached_request_matches()` 与精确 wire 证明兼容路径，不要求旧任务具备新增字段。

现有 SQLite 账本和 content-addressed objects 继续作 L2。历史响应按版本和权限判定可复用；新的过期策略只能影响复用资格，不能删除计费/原文历史。

### P3：补阶段单飞和非唯一索引

写作 FileLock 按稳定的逻辑位置（slot）定位：`SHA256([resolved_database_identity, project_id, task_id, stage, logical_unit_index])`。锁键不含 content_hash、attempt、lease_epoch 或布局版本，避免同阶段换输入或代次后拿到另一把锁并行付费。锁覆盖查询完成响应、预算预留、发送和持久化；获取锁后重新读取任务代次、租约、取消、布局、内容版本和当前权限。

锁内先查该 slot 全部未解决的 pending/sent/outcome_unknown，再判断内容是否匹配。即使内容哈希变化，也不能绕过尚未确认的前一请求。completed_invalid 继续进入既有已保存候选/格式修复流程，不能直接当新缓存 miss 重发。不同 slot 仍可并行；进程内线程必须共享按 slot 注册的同一锁实例，跨进程使用同一规范化文件路径。

锁超时返回“相同请求正在处理”；进程退出释放锁不等于远端没有收到请求。pending/sent/outcome_unknown/completed_invalid 继续阻止自动重发，保留原来的用户确认及格式修复流程。不同任务键仍可并行。

先在隔离副本验证查询计划，再安装以下非唯一辅助索引：

```sql
CREATE INDEX IF NOT EXISTS ai_cache_task_created
ON generation_runs(task_id, created_at DESC);

CREATE INDEX IF NOT EXISTS ai_cache_knowledge_key
ON generation_runs(project_id, json_extract(manifest,'$.knowledge_cache_key'), created_at DESC)
WHERE json_valid(manifest);

CREATE INDEX IF NOT EXISTS ai_cache_outgoing_hash
ON generation_runs(project_id, json_extract(manifest,'$.outgoing_context_hash'), created_at DESC)
WHERE json_valid(manifest);
```

知识查询补上 `json_valid(manifest)`，必要时把 OR 查询拆为按两个键查询后按 run ID 合并。索引不能是唯一索引，因为重试、失败和历史账本允许同输入存在多条记录。

建议新增独立 `scripts/manage_ai_cache_indexes.py` 管理辅助索引，生产空闲后部署；保持 user_version 不变，便于撤回。不要改写已经校验过的旧 migration 文件。若将来纳入正式 schema 升级，必须同步兼容回退版本，不能简单把 CURRENT 从 17 升到 18 后又运行只接受 17 的旧程序。

### P4：保持路由亲和，能力参数按服务商白名单启用

缓存亲和服从 `model_routing._automatic_route()`、`task_scope()`、`call()` 已选定的有效路线：在该路线内，相同材料和模型尽量复用同一合法端点；不得强制恢复原 DeepSeek 端点覆盖任务已经切换的 GPT。DeepSeek 达到配置额度后自动 GPT、GPT 独立有界额度、同任务后续沿用 GPT、任务间隔离均须保留。任务内完成响应命中不修改路由；miss 后才为实际选定端点生成 wire fingerprint。agent 的 messages/tools/items/aliases、能力与账单实际归属不变。

DeepSeek 官方缓存是自动机制，并不要求客户端提供通用的 prompt_cache_key。只有明确支持该参数的其他服务商，才将缓存路由键接入配置和统一 payload。键使用稳定的项目/阶段/前缀版本，不使用每次随机请求 UUID；不能直接把不受支持的参数发给所有中转站。

不为预热缓存额外调用官方 API；默认关闭、手动授权和工作日高峰限制全部保留。中转站的实际缓存能力与上游路由稳定性，需要供应商确认，不能仅凭 OpenAI 兼容协议推定。

### P5：数值检索缓存是独立性能项

`backend/app/knowledge_service.py:95–109` 仍对结构单元逐 chunk 解码并重复归一化。可用按数据库/项目/模型/文本和向量版本隔离的只读矩阵与向量化 dot，按 unit 归并得分；每次仍按当前 eligible 权限过滤。

这主要改善 CPU 和检索延迟，不计入上游 token 缓存节省。先完成 P0/P1，不应让此项延迟核心优化。

收益应分开承诺：

- 可通过离线测试保证：动态编号/错误不再破坏其前方公共材料；可用恢复响应不重新发送；并发相同阶段不会重复预留/发送。
- 需要线上观测：服务商命中率、首 token 延迟、真实支出。首次请求、来源变化、上游缓存清理仍会 miss，不承诺 100% 命中。
- 只读诊断和数值矩阵缓存本身不产生可申报的 token 账单节省。

以截图固定的 3,002,421 输入 token 为测算基数：

| 总输入命中率情景 | 未命中输入 | 相对当前未命中减少 |
|---|---:|---:|
| 当前 26.79% | 2,198,197 | — |
| 60% | 约 1,200,968 | 约 45.37% |
| 70% | 约 900,726 | 约 59.02% |

以上是情景测算和灰度目标，不是已实现的结果。总输入若因去重降低，命中率分母也会变化，应同时比较每次有效产出的输入 token 和真实费用。

在输入总数及输出不变的前提下，费用节省公式为：

```text
节省金额 = 新增命中输入 token × (未命中输入单价 - 命中输入单价) / 1,000,000
```

必须使用实际端点、模型、时段和有版本证据的单价；不能把未命中减少百分比直接当作总账单节省百分比。没有收费测试授权时只做离线验证，不新增模型请求。

## 8. 风险与回退

| 风险 | 控制 | 回退 |
|---|---|---|
| 布局改变影响生成质量或修复行为 | 保留全部语义数据；按任务冻结版本；比较引用、事实与修复合格率 | 仅将新任务默认切回 legacy；在途及可恢复任务继续原版本，保留相应实现至其终止 |
| 排序/字段过滤破坏引用或材料含义 | 只排序声明为集合的内容；版本/权限保留本地；禁止模糊文本归一化 | 暂停新cache_v2任务；既有任务保留原布局，不能在恢复时强制改legacy |
| 完整响应误复用 | 固定同task；fresh generation新操作标识；完整键和命中前校验 | 关闭新增任务内复用，继续保留旧恢复缓存、历史对象和未知结果阻断 |
| 单飞等待/进程故障 | 有界等待、锁内复查；账本状态优先于锁状态 | 先排空相关slot，确认无在途请求并恢复明确串行约束后才撤锁；单worker本身不足以证明无并发 |
| 新参数不被中转站支持 | 能力白名单默认关闭，不自动探测收费能力 | 去掉该端点可选参数；400 不盲目跨接口重试 |
| 索引维护阻塞运行写作 | 先隔离副本验证，生产空闲时执行 | 只 DROP 本方案 ai_cache_* 索引，保留账本及 user_version |
| 缓存折扣误算预算 | 缺失保持未知，计价依据带版本；预留仍保守 | 关闭分价估算，恢复保守预留；不改写历史实际账单 |
| 权限撤销/来源更新被缓存遮蔽 | 保留发送前双重 fresh 校验和复用前校验 | 清除 L1/禁用新增块缓存，仍执行全部原安全检查 |

建议把拟新增开关保存在 `ai_cache_policy` 设置中：`new_task_prompt_layout=legacy|cache_v2`、`stable_block_lru_enabled`、`task_recovery_v2_enabled`、`writing_singleflight_enabled`、`provider_cache_hints_enabled`。这些名称目前是设计项，实施时需要补配置校验与默认值；本方案没有写作跨任务复用开关。LRU可禁用或清空，但不能关闭权限及版本fresh校验。回退不删除账本、对象、未知请求或原件，不强制降低数据库版本。
