## 原因与处理

1. 原请求一次包含 20 个片段。实际 DeepSeek 响应的 8192 个输出 Token 全部用于推理，规则正文为空，最终以 length 结束。现在按最多 4 个片段、约 3500 字分批，要求紧凑 JSON，并使用低推理强度参数。显式关闭推理仍可能被中转站忽略，因此不再单靠这个设置判断兼容。
2. 修复“缺少 rules 字段却当成空结果成功”的问题。无效 JSON、错误来源、无法定位的依据会拒绝入库；明确结束但不可用的结果可在规则整理任务内有限度地交给 GPT。已消费的调用继续留账，不抹去费用。
3. 非流式长请求在实际处理时出现 HTTP 524。规则整理现在请求真实 SSE，同时请求用量元数据；本次余下批次已通过实际流完成。服务商若返回完整 JSON，则按非流式结果校验、记账，不伪造 Token 流。
4. 每批候选、完成记录和进度在同一事务内保存。续接根据来源内容及版本指纹复用已完成批次。超时、取消、预算阻塞和进程中断都不会清空已保存批次。
5. 旧账单逻辑会因同模型存在未决调用而阻塞所有已完成调用的核对。现在只有已完成请求的数量、项目、凭据、模型、币种及 Token 数与账单匹配时，才归并这部分费用；未决调用留在组外并保留预留。本次没有提高项目预算，也没有按猜测填写单价。
6. 当前任务与历史任务分开展示，增加时间、实际模型、已保存批次数和片段计数。旧 403、503、524 等记录仍可展开查看，不会继续混在当前成功状态中。界面提供“继续未完成批次”和“改用 GPT 继续”。
7. 每批保存后刷新候选列表；续接任务明确区分“本轮累计新增”与“本次续接新增”，避免误认为之前已保存的候选丢失。

PDF 换行差异通过仅忽略空白的定位映射还原为原文片段；不通过模糊语义匹配放行数字、否定词或内容变化。
